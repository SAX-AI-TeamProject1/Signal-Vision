# 데이터 수집 일지

`src/dataset/collect.py`로 수신호 학습 데이터를 모으면서 겪은 문제, 원인, 대응을 기록하는 문서.
설계 자체를 다루는 `doc/design.md`와 달리, 실제로 수집해보면서 발견한 UX/데이터 품질 이슈를
시간순으로 쌓아둔다.

## 2026-07-29 — #1. 화면 시작 위치에 좌우 수신호가 좌우되는 문제

### 증상

`left_go`, `right_go` 두 라벨을 각각 60개씩 수집해서 학습해봤더니, 실제 손동작(수신호 모양)과
무관하게 **화면(카메라 프레임) 오른쪽에서 동작을 시작하면 무조건 right_go로, 왼쪽에서
시작하면 무조건 left_go로 분류**됐다. 동작을 반대로 해봐도(오른쪽에서 left_go 동작을 해도)
시작 위치를 따라갔다.

### 원인

`src/capture/extractor.py`의 `FeatureExtractor.vector()`가 MediaPipe 랜드마크 좌표를
**화면 프레임 기준 절대 좌표**(0~1 정규화이지만 원점이 항상 화면 왼쪽 위 고정)로 그대로
저장하고 있었다. 몸(어깨·손목 등) 기준으로 상대화하는 과정이 없었던 것.

라벨당 데이터가 60개 정도로 적으면, 모델 입장에서는 "손이 그리는 궤적의 모양"을 배우는 것보다
"이 시퀀스가 화면 어디서 시작했는가"만 보고 라벨을 맞추는 게 압도적으로 쉬운 지름길이다 —
수집할 때 사람이 항상 화면의 비슷한 위치에 서서 왼쪽/오른쪽으로 향하는 동작을 했기 때문에,
시작 위치와 라벨이 사실상 1:1로 대응돼버렸다. 데이터가 아주 많고 위치가 충분히 다양했다면
모델이 알아서 위치를 무시하는 법을 배웠겠지만, 지금 규모에서는 그 지름길을 그냥 외워버렸다.

### 대응

1. **좌표 정규화 (근본 수정)**: `FeatureExtractor.vector()`가 어깨 중심(랜드마크 11·12 중점)을
   원점으로 손/포즈 좌표를 상대화하고, 어깨너비로 나눠 스케일까지 정규화하도록 수정
   (`_reference_frame()` 추가). 이제 사람이 화면 어디에 서 있든, 카메라와 얼마나 가깝든 같은
   동작이면 같은 특징 벡터가 나온다. `collect.py`(수집)와 `predict.py`(추론)가 이 함수를
   공유하므로 한 번의 수정으로 둘 다 일관되게 적용된다.
2. **기존 데이터 폐기**: 이미 모아둔 `left_go`/`right_go` 데이터는 좌표계가 바뀌기 전(절대 좌표
   기준)에 수집된 것이라 새 코드와 형식이 안 맞는다. 후처리로 좌표를 변환하는 대신, 데이터
   자체가 60개로 적어 재수집 비용이 크지 않다고 판단해 **삭제 후 처음부터 재수집**하기로 결정.

### 다음 수집 시 체크리스트

- 정규화가 들어갔어도, **한 라벨을 수집할 때 화면 안에서 서는 위치(왼쪽/가운데/오른쪽)와
  카메라와의 거리를 의도적으로 바꿔가며 수집**할 것 — 위치·거리와 라벨이 우연히 상관되는
  상황 자체를 피하는 게 정규화만 믿는 것보다 안전하다.
- 라벨당 60개는 다소 적은 편. 가능하면 라벨당 100개 이상, 사람이 여러 각도/속도로 동작을
  반복하도록 목표를 잡는다.
- 수집 후 `src/training/train.py`가 출력하는 혼동 행렬(confusion matrix)을 확인해서 특정
  라벨끼리 계속 헷갈리는지 점검할 것 — 이번처럼 위치 의존 같은 구조적 문제는 정확도 숫자보다
  혼동 행렬 패턴에서 먼저 드러난다.

## 2026-07-29 — #2. 증강(augment.py)이 예전 좌표계 기준(화면 중앙)에 멈춰 있던 문제

### 증상

#1 수정 후 `left_go`/`right_go`를 라벨당 120개씩 재수집하고 재학습했는데, 실시간 추론에서
손을 움직이면 해당 라벨 쪽 확률이 맞게 올라가긴 하지만 **신뢰도가 80%(`predict.py`의 확정
임계값 `--threshold` 기본값)를 넘지 못해 신호가 확정되지 않는** 현상이 계속됐다.

### 원인

`src/training/augment.py`는 `train.py`가 학습 배치마다 호출해 데이터에 무작위 악조건(노이즈·
이동·스케일·렌즈왜곡·손 소실 등)을 섞어주는 모듈이다(val/test·실시간 추론에는 적용 안 됨,
오직 학습 배치에만 적용). 그런데 그중 **스케일 증강(50% 확률)과 렌즈왜곡 증강(30% 확률)**
두 가지가 좌표 중심을 화면 정중앙(`0.5, 0.5`)이라고 가정하고 계산하는 예전 코드 그대로
남아 있었다.

#1에서 `extractor.py`의 좌표계를 화면 절대좌표에서 **어깨 중심 기준 상대좌표(중심 = 0)**로
바꿨기 때문에, 이 두 증강이 걸릴 때마다 이미 0 근처인 값에서 엉뚱하게 0.5를 기준으로
빼고-곱하고-더하는 계산을 하면서 "자연스러운 거리/렌즈 변화 흉내"가 아니라 **매번 크기·방향이
제멋대로인 가짜 이동값**을 학습 데이터에 주입해버렸다. 학습 샘플의 상당수가 이렇게 오염된
채로 들어갔으니, 모델이 깨끗한 결정 경계를 못 배우고 신뢰도가 애매한 수준에 갇힌 것으로 보인다.

정규화 방식을 바꿀 때, 그 좌표를 소비하는 다른 코드(이번엔 증강)에 남아있는 "화면 절대좌표"
가정을 함께 점검하지 않아서 생긴 문제 — 특징 표현 방식을 바꾸는 리팩터링은 그 표현을 쓰는
모든 소비처를 같이 확인해야 한다는 교훈.

### 대응

`augment.py`의 스케일·렌즈왜곡 증강 기준점을 `0.5` → `0`(어깨 중심 원점)으로 수정해 새
좌표계와 맞췄다.

미해결로 남긴 부분: `NOISE_STD`, `TRANSLATE_MAX`, `DISTORT_K`, 렌즈왜곡의 반경 상한(`0.5`) 같은
증강 강도 상수들은 전부 예전 화면 절대좌표(대략 0~1 범위) 기준으로 튜닝된 값이다. 새 좌표계
(어깨너비 단위 상대좌표)에서는 값의 범위 자체가 달라졌을 수 있어(예: 손을 어깨너비 이상
벌리면 1을 넘는 값도 나옴), 이 상수들의 크기가 여전히 적절한지는 검증하지 않았다. 재학습 후에도
신뢰도가 낮으면 다음으로 의심해볼 지점.

### 다음 수집 시 체크리스트 (추가)

- 특징 벡터의 좌표 표현 방식(정규화 기준점·스케일)을 바꿀 때는 `extractor.py`뿐 아니라
  `augment.py`처럼 그 좌표값을 직접 다루는 다른 코드도 같이 점검할 것.
- 재학습 후 신뢰도가 여전히 낮으면 위 "미해결" 항목(증강 강도 상수 재튜닝)부터 확인.
